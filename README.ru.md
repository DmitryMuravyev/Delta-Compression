<h1>Что это и для чего это надо</h1>

Это простой и легковесный компрессор/декомпрессор, основанный на методе дельта-кодирования. Я планировал его как небольшой вспомогательный модуль для вывода микроконтроллером графики на дисплей, но немного увлёкся и проект получился достаточно масштабный. Тем не менее, основное его предназначение - уменьшение размера с последующей декомпрессией и выводом на экран элементов интерфейса. Технология может быть полезна в эмбедированных системах мелкого и среднего уровня (среди примеров я сделал [один для ATtiny85](/Examples/AVR/ATtiny85)).

Приложение компрессора работает в Windows и Linux (оно написано на .NET 10 и Avalonia и не требует установки .NET), а для декомпрессии я подготовил несколько вариантов исходного кода, отличающиеся своими возможностями и производительностью.  

И, конечно, проект может быть использован для компрессии любых данных.

<h1>Как это работает</h1>

Для компрессии используется метод дельта-кодирования: вместо того, чтобы хранить оригинальную последовательность данных, мы храним только разность (дельту) между каждыми двумя соседними значениями. И в случае с графическими данными это даёт неплохую (во всяком случае нестыдную) степень компрессии.

<h2>Алгоритм сжатия (версия 2)</h2>

Данные это последовательность кадров (пикселей), в каждом кадре 1–4 канала. Компрессор разрезает последовательность на блоки. У каждого блока есть заголовок (длина блока в поле из *b* бит и номер метода для каждого канала), за которым идут данные каналов. Для каждого канала блока выбирается один из трёх методов:

- **Фиксированное окно**: значения блока помещаются в окно шириной 2<sup>w</sup>, начинающееся с минимума блока. Стоимость: *k + l·w* бит (*k* битность канала, *l* длина блока).
- **Адаптивное плавающее окно**: каждое значение хранится относительно окна шириной 2<sup>w</sup> вокруг предыдущего значения. Стоимость: *k + (l−1)·w* бит.
- **Без сжатия**: *l·k* бит.

Версия 1 строила цепочку жадно: в каждой позиции искала блок с наилучшей эффективностью и шла дальше. В версии 2 изменился способ выбора цепочки; формат потока и декомпрессор остались прежними.

**1. Наименьшая цепочка, а не самые эффективные блоки.** Очень эффективный длинный блок может оставить хвост, который плохо сжимается, а короткий слабый блок может открыть дорогу гораздо лучшему. Поэтому версия 2 минимизирует общий размер напрямую, динамическим программированием по всем данным. Если Bits(p, l) размер самого дешёвого блока длины *l*, начинающегося с кадра *p* (каждый канал независимо берёт свой самый дешёвый метод, который выдерживает *l* кадров), то наименьший размер данных от кадра *p* до конца равен

$$\mathrm{Best}(N) = 0, \qquad \mathrm{Best}(p) = \min_{1 \le l \le \min(2^b,\ N-p)} \left(\mathrm{Bits}(p,l) + \mathrm{Best}(p+l)\right)$$

Best считается от последнего кадра к первому с запоминанием лучшей длины блока в каждой позиции, затем цепочка читается вперёд и записывается. Любой поток, который принимает декомпрессор, это цепочка таких блоков, поэтому ни один поток не может быть меньше Best(0): для выбранных настроек получается наименьший возможный файл. Пример (*k* = 8, *b* = 3, кадры 97 97 117 117 117 116 116 117 117 117): жадная цепочка занимает 70 бит, оптимальная 38 бит.

Чтобы это работало быстро, перебор *l* останавливается, как только одно Bits(p, l) достигает лучшего найденного итога (Bits только растёт с *l*), стоимость блока линейна по *l* между точками смены метода, а длины окон в кадре *p* обновляются из длин в кадре *p + 1*, а не пересчитываются заново. Изображение 240×240 обрабатывается примерно за 0,1 с.

**2. Все ширины окна за один проход.** Более широкое окно всегда держится не меньше, чем узкое, поэтому один проход по данным даёт длины для всех ширин окна (*w* = 0, 1, 2, …), а не по проходу на каждую ширину.

**3. Точный поиск наилучшего блока.** Покадровый режим больше не перебирает все комбинации методов (4096 на кадр для RGB888). Длина блока может быть только одной из длин самих методов; для каждой такой длины *l* каждый канал берёт свой самый дешёвый метод, выдерживающий не меньше *l* кадров, а один канал берёт самый дешёвый метод, заканчивающийся ровно на *l*. Это даёт тот же блок, что и полный перебор, байт в байт, примерно в 90 раз быстрее, поэтому прежний «быстрый» вариант поиска убран.

**4. Автоматический подбор настроек (Auto).** Оптимальная цепочка даёт точный размер файла без его записи, поэтому приложение может перебирать настройки: все сочетания размера квадратов и варианта вычисления дельты, и для каждого поле длины блока (*b*) от меньшего к большему, пока размер не вырастет три раза подряд. Побеждает наименьший результат.

Результаты на тестовом наборе по сравнению с версией 1 с настройками из спринтов: одна оптимальная цепочка даёт файлы меньше на 0–5%, настройка Auto до 24% (например, Icons RGB888 29382 → 22203 байт, Logo RGB888 26734 → 22903 байт), а весь набор сжимается за 2,9 с вместо 53,7 с. Каждый результат проверяется распаковкой неизменённым декомпрессором. Подробности, доказательства и полная таблица в [docs/v2-changes.md](/docs/v2-changes.md) (на английском) и в [презентации Спринта 4](/docs/Sprint_4_Mathematical_foundation.pdf).

<h1>Возможности</h1>

- Поддержка изображений с размером до 65535 x 65535 пикселей;
- до 4 каналов данных (R/G/B/A, L/R, и т.д.);
- до 32 бит на канал;
- до 64 бит на кадр (для большей ширины кадра требуется модификация декомпрессора);
- за 1 запрос можно распаковать до 2^32 кадров (пикселей) или до 2^32 упакованных/распакованных данных;
- декомпрессия кадров шириной 1-2-4 бит;
- разбиение изображений на квадраты;
- сжатие произвольной глубины цвета для каждого из каналов;
- преобразование в оттенки серого;
- сжатие альфа-канала;
- 4 варианта вычисления дельты;
- наименьшая возможная цепочка блоков для выбранных настроек (динамическое программирование по всем данным);
- автоматический подбор поля длины блока, варианта вычисления дельты и размера квадратов (настройка Auto);
- PNG-изображения читаются с точной битностью (1/2/4/8/16 бит оттенки серого, 8/16 бит цвет, палитра, альфа);
- поддержка доступа в "дальнюю" память AVR*;
- разбиение сжатых данных на части (до 32767 байт)*;
- создание заголовочного файла со сжатыми данными и их описанием. Вам надо будет только включить этот файл в ваш код и передать ссылки на объявленные в нём константы в процедуру декомпрессии;
- компрессия произвольных файлов с возможностью разбиения на каналы и выбора ширины каналов (пока доступны только варианты, кратные 8-ми битам);

\* Относится только к платформе AVR.

<h1>Как пользоваться</h1>
<h2>Компрессия</h2>

![Application](/docs/images/screenshot-image.png)

Приложение для сжатия данных содержит 2 вкладки: для изображений и для любых других файлов. После открытия изображения или файла вы можете настроить желаемую конфигурацию каналов (или формат пикселя) и выбрать режим разбиения на квадраты для изображений.
В области предварительного просмотра можно видеть как будет выглядеть изображение (или данные, разбитые на каналы) с применением выбранной конфигурации.  

Параметры сжатия настраиваются в нижней части окна:
- Количество бит на поле длина блока. Чем больше это поле, тем более длинные блоки сможет создавать алгоритм сжатия. Этот параметр настраивается индивидуально для каждого конкретного экземпляра данных и обычно находится в диапазоне 5-8 бит.
- Способ вычисления дельты. Фиксированное Окно больше подходит для малоконтрастных шумов, а Адаптивное Плавающее Окно лучше подходит для градиентов (см. ссылки выше). Также доступны их комбинации.
- Настройки (Settings): ***Manual*** использует выбранные вами поле длины блока, метод вычисления дельты и квадраты. ***Auto*** (по умолчанию) перебирает поля длины блока, методы вычисления дельты и размеры квадратов, оставляет вариант с наименьшим файлом и показывает его в соответствующих полях. Так как Auto может выбрать любой метод и размер квадратов, сверьтесь с генерируемым .h-файлом и настройте декомпрессор соответственно (см. раздел Декомпрессия).
- Выбор платформы, для которой будет сгенерирован заголовочный .h-файл. Единственное отличие AVR от других платформ заключается в том, что в определение константы массива добавляется макро-символ "PROGMEM", и через каждые 16384 байта массива выдается предупреждающий комментарий о превышении этого порога. Для других платформ эти действия не выполняются (конфигурация платформ и возможностей генерации кода может быть настроена и находится рядом с приложением в файлах: [appsettings.json](/src/DeltaComp.App/appsettings.json), [Header_Source.xml](/src/DeltaComp.App/Header_Source.xml), [Header_Transformation.xslt](/src/DeltaComp.App/Header_Transformation.xslt)).



После нажатия на кнопку "Compress" и выбора пути сохранения файла, сначала выполняется анализ данных (голубой прогресс-бар), а потом компрессия и запись массива в выходной файл (зелёный прогресс-бар).  
${\color{red} Внимание!}$ Название файла будет использовано в качестве основы для макро-имён и имён констант в генерируемом файле.

<h2>Декомпрессия</h2>

Для корректной распаковки вам нужно всего лишь настроить несколько параметров в файле [Decompression.h](/Decompression/Decompression.h):

- Используя символы комментирования '//', выберете один из вариантов вычисления дельты. Обратите внимание, что выбирая, например, опцию DECOMPRESSION_FIXED_WINDOW_FIRST вы сможете распаковывать не только данные, сжатые с применением этой опции, но и данные, сжатые с помощью только Фиксированного Окна. И наоборот, выбирая опцию DECOMPRESSION_ADAPTIVE_FLOATING_WINDOW_FIRST, вы сможете распаковывать данные, сжатые как при помощи Адаптивного + Фиксированного, так и только Адаптированным Окном:

```C
//#define DECOMPRESSION_FIXED_WINDOW_ONLY
//#define DECOMPRESSION_ADAPTIVE_FLOATING_WINDOW_ONLY
#define DECOMPRESSION_FIXED_WINDOW_FIRST
//#define DECOMPRESSION_ADAPTIVE_FLOATING_WINDOW_FIRST
```

- Задайте максимальное количество каналов (например, R/G/B = 3 канала), которое будет распаковываться в вашем продукте:

```C
#define DECOMPRESSION_MAX_NUMBER_OF_CHANNELS	3
```

- Определите, будут ли распаковываться изображения, разбитые на квадраты:

```C
#define DECOMPRESSION_USE_SQUARES
```

- А для платформы AVR вы можете определить, будет ли использоваться разбиение сжатых данных на части (для массивов, превышающих 32767 байт):

```C
#define USE_FAR_MEMORY_CHUNKS  
#define CHUNK_SIZE	16384
```

Дополнительно, если используется разбиение на квадраты, то для корректной распаковки вам надо задать значение ширины буфера в пикселях (в коде основной программы):

```C
static Decompression decomp;
decomp.bufferWidth = LOGO_IMAGE_WIDTH;
```

И не забывайте сбрасывать переменные среды декомпрессора перед распаковкой каждого следующего объекта:

```C
decomp.resetDecompression();
```

Вот и все! Как видите, всё довольно просто!

```sh
dotnet publish src/DeltaComp.App -p:PublishProfile=win-x64
dotnet publish src/DeltaComp.App -p:PublishProfile=linux-x64
# Результат в artifacts/publish/<runtime>/

# Тесты: UI-тесты без дисплея, бенчмарк с побайтовой проверкой
dotnet test tests/DeltaComp.App.Tests
dotnet run -c Release --project tests/DeltaComp.Bench -- --optimal
```

Avalonia собирает анонимную телеметрию во время сборки; чтобы её отключить, задайте переменную окружения `AVALONIA_TELEMETRY_OPTOUT=1`.
